# ecommerce-GO-microservices

A small e-commerce platform built as Go microservices: REST between services, events over RabbitMQ, one PostgreSQL database per service, Prometheus and Grafana for monitoring. It runs on Docker Compose and Kubernetes.

```
client ──► gateway :8080 ──► user-service    :8081 ─► users_db
                        ├──► product-service :8082 ─► products_db
                        └──► order-service   :8083 ─► orders_db
                                   │  ▲
                 order.created     ▼  │ stock.reserved / stock.rejected
                              RabbitMQ (exchange "ecommerce.events")

Prometheus scrapes GET /metrics on every service ─► Grafana dashboard
```

## Order lifecycle

1. `POST /orders`: the order-service checks the user and reads prices over REST, then stores the order as `pending` (response `202`).
2. The product-service consumes `order.created` and reserves stock for every line, or for none.
3. The order-service consumes the result and moves the order to `confirmed` or `cancelled` (with a `reason`).

## Design choices and the problem each one solves

| Choice | Problem solved |
|---|---|
| Layers `domain → storage / httpapi / messaging`, interfaces declared in the domain | Business logic depends on neither PostgreSQL nor HTTP, so it is tested with fakes (`order_test.go`) |
| Transactional outbox (`platform/outbox`) | A crash between COMMIT and publish would lose the event and leave the order `pending` forever |
| `processed_orders` table and `UPDATE … WHERE status = 'pending'` | RabbitMQ delivers at least once: a replayed message must not take stock twice |
| `UPDATE … WHERE stock >= quantity` | Two concurrent orders cannot sell the same item |
| Prices in integer cents, frozen in the order | No rounding errors; a price change does not alter past orders |
| Shared `platform` module | Database, broker, HTTP server, metrics and event contracts are written once |
| Metrics labelled by route pattern (`GET /users/{id}`) | Labelling by raw path would create one time series per id |
| One root `Dockerfile` with a `SERVICE` build arg | Four identical Dockerfiles would drift apart |
| Secrets as files, one database role per service | See [Configuration and secrets](#configuration-and-secrets) |

## Project layout

```
platform/          shared module: postgres, rabbitmq, outbox, events, httpx, server, metrics
user-service/      cmd/ + internal/{user, storage, httpapi}
product-service/   cmd/ + internal/{product, storage, httpapi, messaging}
order-service/     cmd/ + internal/{order, storage, httpapi, messaging, clients}
gateway/           reverse proxy, the only exposed entry point
deploy/config/     config shared by Compose and Kubernetes (Postgres init, Prometheus, Grafana)
deploy/base/       Kubernetes manifests, without any secret
deploy/overlays/   dev (generated secrets) and production (External Secrets)
scripts/           secret generation, end-to-end smoke test
.github/workflows/ CI/CD pipeline
```

## Configuration and secrets

**No secret is stored in this repository**, and CI enforces it with a [gitleaks](https://github.com/gitleaks/gitleaks) scan of the whole history.

| Practice | Why |
|---|---|
| `.env.example` is committed; `.env` is generated by `scripts/init-secrets.sh` with random passwords and git-ignored | A committed password stays in the git history forever |
| Passwords reach the services as **files** (`DB_PASSWORD_FILE`, `MQ_PASSWORD_FILE`): Docker secrets in Compose, Secret volumes in Kubernetes | Environment variables leak through `docker inspect`, `/proc/<pid>/environ`, child processes and crash reports |
| **One PostgreSQL role per service**, owner of its database only, `CONNECT` revoked from everyone else | A compromised service cannot read the other services' data |
| **One Kubernetes Secret per consumer** | Each pod only mounts the credentials it needs |
| Typed config (`platform/config`) validated at startup, listing every missing setting | A misconfigured service refuses to start with a clear message instead of failing later |
| Connection strings built in code with escaping; `Config.String()` redacts the password | A generated password containing `@` or `/` would break a hand-written URL; logging a config must not leak it |
| Production overlay uses the [External Secrets Operator](https://external-secrets.io) | Secrets live in a secret manager (AWS, GCP, Vault…), are rotated there and synced into the cluster |

Each service reads:

| Variable | Services | Default |
|---|---|---|
| `PORT` | all | 8080–8083 |
| `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD_FILE` (or `DB_PASSWORD`) | user, product, order | — |
| `DB_PORT`, `DB_SSLMODE` | user, product, order | `5432`, `prefer` |
| `MQ_HOST`, `MQ_USER`, `MQ_PASSWORD_FILE` (or `MQ_PASSWORD`) | product, order | — |
| `MQ_PORT` | product, order | `5672` |
| `USER_SERVICE_URL`, `PRODUCT_SERVICE_URL` | order, gateway | — |
| `ORDER_SERVICE_URL` | gateway | — |

Known limitation: the official RabbitMQ image has no `*_FILE` option, so the broker's own password is injected as an environment variable, still sourced from `.env` or a Kubernetes Secret.

## Run with Docker Compose

```sh
scripts/init-secrets.sh            # once: generates .env (set GATEWAY_PORT there if 8080 is taken)
docker compose up -d --build
scripts/smoke-test.sh http://localhost:8080
```

| URL | |
|---|---|
| http://localhost:8080 | API gateway |
| http://localhost:3000 | Grafana, "E-commerce overview" dashboard (anonymous view; `admin` / `GRAFANA_ADMIN_PASSWORD` to edit) |
| http://localhost:9090 | Prometheus |
| http://localhost:15672 | RabbitMQ management (`RABBITMQ_USER` / `RABBITMQ_PASSWORD`) |

All credentials are in your local `.env`.

## Run on Kubernetes (minikube)

```sh
minikube start
scripts/init-secrets.sh                    # writes deploy/overlays/dev/secrets/ (git-ignored)
docker compose build                       # build the images locally
for s in user-service product-service order-service gateway; do
  minikube image load ghcr.io/oubeidhanini/ecommerce-go-microservices/$s:latest
done
kubectl apply -k deploy/overlays/dev
kubectl -n ecommerce wait --for=condition=Ready pod --all --timeout=300s

kubectl -n ecommerce port-forward svc/gateway 8080:80 &
scripts/smoke-test.sh http://localhost:8080
kubectl -n ecommerce port-forward svc/grafana 3000:3000   # admin / GRAFANA_ADMIN_PASSWORD
```

For production, `kubectl apply -k deploy/overlays/production` expects the External Secrets Operator and a `ClusterSecretStore` named `production-secrets`, holding the keys listed in `deploy/overlays/production/external-secrets.yaml`.

curl -s -X POST localhost:8080/users    -d '{"name":"Ada","email":"ada@example.com"}'

## Load test (k6)

```sh
docker compose --profile loadtest run --rm k6                                    # 100,000 requests, 200 virtual users
docker compose --profile loadtest run --rm -e REQUESTS=20000 -e VUS=100 k6       # smaller run
```

The script ([loadtest/load.js](loadtest/load.js)) sends 90% product reads and 10% orders through the gateway, then checks that every order was confirmed and that the stock dropped by exactly that many units: no lost event, no double reservation. Watch it live on the Grafana dashboard.

Results on a laptop (8 CPUs, Docker Desktop with 3.8 GB), whole stack on one machine:

| | First run | After tuning |
|---|---|---|
| 320,000 requests | — | **27 s, ~3,650 req/s**, 0 errors |
| p95 / p99 latency (10k run) | 546 ms / 5.99 s | 89 ms / 162 ms |
| Consistency check | passed | passed (9,905 orders, stock exact) |

What the load test revealed and fixed:
- **Go's HTTP client keeps 2 idle connections per host.** Under load, the gateway and the order-service opened a new TCP connection for most requests: p99 was 4.5 s at the gateway but 0.25 s inside the product-service. Fixed with a shared, tuned transport (`httpx.Transport`).
- **The outbox relay was capped at 200 events/s** (100 per 500 ms tick). It now drains full batches immediately and deletes each batch in one query.

## CI/CD (`.github/workflows/ci.yml`)

| Job | Runs on | What it does |
|---|---|---|
| `secrets-scan` | every push and PR | gitleaks scan of the full git history |
| `test` | every push and PR | `gofmt`, `go vet`, `go test -race` for each module, built on its own (`GOWORK=off`) |
| `manifests` | every push and PR | renders both Kubernetes overlays |
| `e2e` | every push and PR | generates throwaway secrets, starts the stack with Compose and runs the smoke test |
| `images` | push to `main` | builds and pushes the images to GHCR, tagged with the commit SHA and `latest` |
| `deploy` | push to `main` | pins the images to the commit SHA and applies `deploy/overlays/production`; skipped until a `KUBECONFIG` secret is added to the `production` environment |
